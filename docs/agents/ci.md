# CI and Workflows

Legacy v2 integration migration is tracked in #14950. The legacy v2 workflow is retired on master; the API workflow enforces its replacement coverage. Keep its completion-event subscription in `ci-checks.yml` while release branches still run it, so release reruns update `ci-passed`. Existing assertion parity and CI evidence are recorded in `backend/test/v2/api/legacy-migration.md`. The API workflow verifies the migration manifest against actual Ginkgo JSON reports in cache-enabled standalone and Kubernetes-native jobs; cache-disabled standalone jobs exclude cache-hit assertions. The retired API harness and its unused cleanup/diagnostic helpers are removed. The integration directory retains the standalone webhook tests and Makefile; database initialization remains in `backend/test/integration`.

GitHub Actions workflows are in `.github/workflows/`; reusable composite actions are in `.github/actions/`.

- Frontend Node consumers read `frontend/.nvmrc`; update its exact version together with the frontend manifest and lockfile engine. The dependency configuration tests guard these pins, shared CI/image consumers, and npm's strict engine enforcement. jsdom 30's CSS dependency tree requires at least Node 24.15.0 on the Node 24 line.

- The Kubernetes-native migration experiment-creation test uses a 60-second polling budget for a reported run state. Initial Workflow persistence may temporarily omit the state before Argo reports a phase. API errors and observed failed/canceled runs fail immediately; an unreported state times out with the run ID and log guidance. CI Scripts Tests covers delayed state, timeout, and error behavior without a cluster.

- Update this guide when changing workflows, CI matrices, commands, generated outputs, or common failure handling.
- `release-qualification.yml` disables all GitHub Actions cache access with workflow-level `cache-mode: none` (no job overrides), since repository read-only permissions do not isolate cache tokens when executing selected source. It is a read-only `workflow_dispatch` workflow for all release qualification builds and scans. Trusted tooling comes from `github.workflow_sha`; release source is checked out at the requested full SHA with credentials disabled. Source dependency scanning runs before wheel generation and requires root Go/frontend lockfile coverage. Source-only blank-version lockfile declarations without findings are preserved in a verified `unresolved_inventory` as unaudited inputs, matching the limitation of manifest-only scanning; they cannot satisfy required Go/frontend coverage. Installed Python and image inventories remain strict about resolved versions. The SDK job builds wheels once, qualifies every Python minor advertised by that source, and scans each exact installed distribution inventory, including qualified local packages. Executable environments stay outside uploaded evidence; freezes, compiled pipelines, command logs and checksummed wheels are retained. Native AMD64/ARM64 image lanes use the source commit's release matrix and exclusions, build without registry login or push, and scan verified immutable Docker archives. All qualification scans use checksum-pinned OSV Scanner 2.5.0 with empty configuration and complete JSON package/vulnerability output. Source/Python coverage, scanner exits, archive/image identity and all evidence checksums must validate before aggregation. The attempt-bound `kfpr-images-<request_id>-<run_attempt>` artifact binds scope, source/tool SHAs, request/run/attempt, all image/platform lanes and all declared Python minors; source/Python evidence is under `security/`. The local client verifies the complete artifact and live run, then applies the selected fixability/exception policy centrally; CI does not silently waive findings. Exception aliases match only within the exact scope, artifact, package and installed version, and expiry is rechecked at publication. Generated tracked source changes require a new version PR. Qualification is CI-only: legacy local modes and interpreter overrides are rejected, and old Trivy or SARIF-only receipts cannot satisfy the OSV JSON contract. SDK-only releases skip images; backend-only releases skip wheels; source scans always run. The workflow must merge upstream before dispatch. Test using `PYTHONPATH=release python -m unittest kfpr.ci_qualification_client_test kfpr.ci_qualification_runner_test kfpr.ci_security_runner_test kfpr.osv_reports_test` plus the image runner and workflow contract tests.
- `release-branch-image-scanning.yml` runs centrally from master for `release-2.18`: any completed same-repository `pre-commit` push run wakes it, with weekly and manual recovery. Lint failures do not suppress image security scans. The resolver validates the triggering workflow/repository/branch and reads the current release branch SHA, so late events scan current code. Runs serialize per tool branch; unrelated events cannot replace pending scans. Tooling comes from `github.workflow_sha`; the literal release source checkout is immediately checked against its resolved full SHA. Its own VERSION and image/platform matrix define the build. The shared qualification runner builds native lanes without registry login or publication. Branch scans explicitly select checksum-pinned OSV 2.5.0, export each immutable local image to a Docker archive, verify the archive config digest matches the image ID, and scan that archive without registry fallback. Evidence binds the image ID, archive checksum, scanner identity, exit status and unfiltered SARIF to the source/tool/request/run attempt. Exit codes other than 0/1, missing packages/reports, mixed scanners, missing lanes or checksum mismatches fail closed. Complete aggregate validation precedes extraction of the unchanged OSV SARIF; clean scans retain valid empty results. Only the separate master-only upload job has `security-events: write`, with exact release SHA/ref and stable image/platform categories. Manual candidate-branch dispatches build and validate all artifacts but skip upload; they cannot clear release alerts. Release qualification also uses OSV, but retains full JSON evidence for fixability policy; branch alert uploads retain SARIF. Test using `PYTHONPATH=release python -m unittest kfpr.branch_scan_test kfpr.ci_images_runner_test kfpr.osv_image_scan_test` plus the release branch workflow contract test. Scanner migrations require successful merged-workflow uploads for every expected lane before deleting old scanner configurations.

- `pr-gate.yml` skips PRs authored by `dependabot[bot]` or `copybara-service[bot]`, regardless of the event actor. For other PRs, membership comes exclusively from the `admins` and `members` lists in `kubeflow/internal-acls/github-orgs/kubeflow/org.yaml`, using a case-insensitive username match rather than GitHub's `author_association`. The gate and contributor report share `.github/scripts/kubeflow_membership.py`, which reads the ACL from `master` through the authenticated `gh` CLI and raises on lookup errors instead of returning a negative result. Both workflows check out the helper and `.github/scripts/requirements.txt` only from `github.workflow_sha`; the gate also checks out `.github/scripts/pr_gate_issue.py` from that trusted commit. The helper uses a PyYAML `SafeLoader` subclass that rejects duplicate mapping keys (including merge overrides) and validates the membership lists; lookup failures, malformed YAML, or invalid membership data fail the workflow without closing the PR. The gate, report, and CI Scripts Tests install the shared pinned requirements using Python 3.13. Authors absent from the ACL must reference an issue in this repository with the exact `ready` label. The gate uses GitHub's closing issue links and, for non-default-branch PRs where GitHub does not create a link from a closing keyword, accepts an explicit closing reference on its own line in the PR body. It closes PRs without an eligible issue. Both closure paths use the same contribution-focused message with a direct link to the [external-contributor admission guidelines](../../CONTRIBUTING.md#pull-request-admission-for-external-contributors). This author-specific exemption does not approve other workflow runs or bypass merge requirements.
- After admitting an external contributor, `pr-gate.yml` adds `ok-to-test`, removes any existing `needs-ok-to-test`, and approves pending `pull_request` runs for that PR's current head through the Actions API. It checks the live PR state and labels, requires the fork repository, branch, and SHA to identify exactly one open PR, and filters runs to that head. The gate cannot rely on its `GITHUB_TOKEN` label change to trigger `gh-workflow-approve.yml`; GitHub suppresses that labeled event. The separate approval workflow still handles trusted authors and labels applied by maintainers, with the same unique-head guard, and sweeps admitted open PRs every 15 minutes for runs that appear after the gate's polling window. A later conflicting `needs-ok-to-test` label blocks automatic approval until fresh admission or maintainer review. CI Check reconciles `ci-passed` when the approved workflows complete.

## Workflow credentials and settings rollout

Every job must have explicit, enumerated token permissions, directly or through
its workflow default. Ordinary builds and tests use `contents: read`; jobs that
look up artifacts from other runs or poll jobs/artifacts through the REST API
also need `actions: read`. Same-run artifact upload/download and cache operations
do not require `actions: write`.
Reusable-workflow callers must explicitly allow the permissions their callees
need: a callee cannot elevate a read-only caller. Do not use `secrets: inherit`
when the callee only needs the automatically available `GITHUB_TOKEN`.

Keep write scopes on the jobs that use them:

- Image publication retains `packages: write`, `attestations: write`, and
  `id-token: write`. The separate image dry-run job shares the same build steps
  but has only `contents: read` and `packages: read` for registry inspection.
  Manifest promotion needs `packages: write`, not OIDC. Native tools PR builds
  are read-only; trusted staging and verified-index promotion retain package
  writes and the architecture comparison gate.
- Python distribution selection, builds, and validation are read-only. Only
  the separate non-dry-run PyPI upload job receives `id-token: write`; it consumes
  validated distributions from the same workflow run, not source code. A
  checksum manifest verifies the complete wheel/sdist inventory before upload,
  without checking out code in the OIDC job. Stable per-package artifact names
  let failed publisher jobs retry without rebuilding or republishing successful
  packages; a rerun of the build replaces only that package's same-run artifact.
  Keep checkout-independent setup and source-tag package selection so legacy
  four-distribution releases continue to work.
- Metadata workflows retain only their actual label/comment/status and
  workflow-approval permissions. The analyzer's `actions: write` is intentional:
  invalid or ignored title edits and rate-limited runs self-cancel to preserve
  quota behavior. Do not remove this scope without replacing that contract.
  Runtime-cache pruning and security-report uploads also retain their required
  write permissions.

Use `persist-credentials: false` on checkouts; explicitly scope any subsequent
authenticated operation instead of leaving the token in Git configuration.
Frontend base-ref fetches use the public repository without stored credentials.
External actions are pinned to full commit SHAs with version comments, including
actions inside composites. Dependabot continues to propose reviewed updates.
The workflow permission regression suite guards explicit scopes, intentional
writes, reusable caller/callee contracts, and credential persistence.

Repository settings are a **separate, post-merge rollout**, not part of deploying
these YAML changes:

1. Merge and validate the workflow changes on `master`. Before reducing the
   repository token default, audit and minimally backport explicit image-build
   and publication caller contracts to every supported release branch,
   including `release-2.18`. Preserve each branch's legacy image inventory and
   release architecture policy; do not replace it with the master workflow.
2. After those changes merge and representative CI and release dry runs pass,
   change the default token permission to read-only and disable Actions-created
   or Actions-approved pull requests. The latter does not disable approval of
   pending workflow runs. Verify metadata jobs and subsequent release runs.
3. Enable required SHA pinning only after supported release refs and every
   allowed external action/reusable-workflow dependency are compatible. Review
   an action allowlist separately; do not block existing third-party reusable
   workflows or old release tags as a side effect of lowering token defaults.

Do not add `environment: pypi` until the PyPI Trusted Publisher configuration
accepts that environment's OIDC identity and its GitHub deployment policies
permit all supported publishing refs. The upload-job split preserves the
existing workflow identity; environment protection is a coordinated follow-up,
not an unverified credential change. Never publish images or packages merely to
test the permissions rollout.

See GitHub's [secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use)
and [reusable-workflow permission rules](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations).

The Python visualization service is retired. Image builds, CI artifact inventories, and Kustomize overlays exclude it; v2 artifact viewers and the TensorBoard viewer controller remain supported. See [artifact migration and deployment cleanup](../concepts/output-artifact.md#migrating-from-the-python-visualization-server).

It verifies full indexes and unchanged versioned tags and always uploads partial/success evidence. Dispatch through `kfpr promote-latest --version X.Y.Z`; this workflow must first be merged upstream. Test with `PYTHONPATH=release python -m unittest kfpr.promotion_test`.

- Release branch image scanning checks out the literal trusted `refs/heads/release-2.18` in each job, then immediately requires its HEAD to match the selected full SHA before running subsequent steps. This keeps dynamic revisions out of master-cache-context checkouts. If the branch advances between jobs, the scan fails closed without uploading a mixed revision; the next queued push or a manual retry scans the new head.
- OSV image discovery downloads the exact successful producer SHA as a data archive and extracts only regular files under `manifests/`, rejecting traversal and links. Scanner tools remain at `github.workflow_sha`. Image scan attribution checks out the producer only after executable scan steps, immediately before SARIF upload; its git HEAD must match the reported producer SHA.
- The offline frontend qualification reliability reporter preserves first-attempt job outcomes across reruns and cancelled workflows; it does not retry jobs or promote qualification gates. See [collection and interpretation](../contributing/frontend-qualification-reliability.md). Missing attempt evidence remains unknown.

The frontend qualification reliability reporter supports `--collect --repository OWNER/REPO --since YYYY-MM-DD --until YYYY-MM-DD` with repeated `--workflow` selections. Collect into an empty directory; preserve raw attempt responses and `collection.json`. Bounds, pagination and unchanged-run identities are verified before the collection is marked complete. Collection failure remains explicit and does not publish a success report; rerun into a new directory. Scheduling, deduplicated alerts and maintainer ownership remain separate prerequisites for monitoring. See [the contributor guide](../contributing/frontend-qualification-reliability.md).

- API cache scenarios use Ginkgo priority to start their long-running work before ordinary parallel specs. Cache-enabled standalone/Kubernetes-native jobs and multi-user shard B prepare offline fixture images with the original released SDK/Python matrix: kfp 2.13.0 on Python 3.12 and kfp 2.14.2 on Python 3.11. SDK wheels are prepared once per job (2.13.0 is built from its published sdist) then installed with --no-deps into preloaded bases without network access. Only fixture installer prefixes and images change; component source, arguments, outputs and PVC configuration remain intact. These cache fixtures do not consume checked-out SDK sources. Other API fixtures retain normal SDK installation. Include wheel and image preparation in wall-time comparisons; required migration labels and cache assertions remain unchanged.

- The deploy action first restores the existing runtime-image cache using the producer’s exact source fingerprint, UTC date, and archive paths; matrix jobs never save caches. A missing, failed, or incomplete restore falls back to the same-run runtime artifact with digest checking and bounded recovery. Both archives must be nonempty before accepting a cache hit, and all required image tags are still verified in Kind. Runtime preparation overlaps branch image builds; the later barrier and positive download pattern select only the seven branch images. The two archive inventories preserve optional Modelcar coverage. Measure the full job, including cache misses: artifact transfer/extraction variability can dominate cluster setup.
