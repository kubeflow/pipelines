# MLMD migration PR 3 fix design

Reviewed `a69de61f74..dc839dbf38`, including the inherited planner where it affects the complete migration. The implementation plan and dedicated database migration design govern cutover and historical mappings. The runtime design supplies the requirements for reading and using the migrated history.

**Release decision.** Hold production enablement. The pinned data-path checks establish useful fixture coverage. The branch still needs runnable upgrade CI, a database cutover that satisfies repository policy, and the compatibility fixes below.

Keep the focused interruption and writer-refusal checks in presubmit. Exercise a new pipeline and a recurring run after cutover to cover the runtime path as well as historical reads.

## 2. Keep production migration disabled until the database cutover qualifies

**Attempt to disprove.** The dedicated design explicitly requires old replicas to drain and stop. That explains the operational fence. The implementation plan separately requires qualification under the repository's nonblocking database policy before production use. The engine creates its target table separately and swaps names atomically, so it avoids an implicit full copy inside the rename. On MySQL 8.4.10, `TestMySQLCutoverRespectsSessionLockTimeout` passed. It proves an unrelated write completes while the rename waits and that the related write survives the bounded DDL timeout. Its related-write assertion has no requirement that the write complete while the rename is pending. The production paths also require writer shutdown before the data copy. I found no qualification or documented decision resolving that conflict in the reviewed tree.

**Immediate implementation.** Keep the legacy classifier and add an actionable startup refusal before GORM schema reconciliation. Keep production Phase 2/3 unreachable through API startup and the shipped CLI, including cleanup of any partially migrated catalog. Check pending transfer identity reconciliation independently of the MLMD migration state. A catalog can have completed MLMD validation and still require the transfer table rename. Preserve read-only preflight and the test-only path used on disposable databases. Withdraw the mutating `cutover.sh` procedure from production instructions during the hold and have any shipped copy exit before the first scale operation. Preflight success only establishes that its read-only checks passed. In release instructions, keep legacy installations on the supported 2.18 release until the cutover qualifies. Production binaries provide no bypass.

**Replacement design to qualify.** Stage additive native task and lineage storage in a bridge release. Leave the active legacy task table in place and audit startup DDL and transfer identity storage as part of the same upgrade. The bridge routes new executions to native storage and lets existing legacy executions finish on their original runtime. Keep legacy reads authoritative for each legacy run until the final report and migration validation pass. Use a durable per-run boundary tied to the run's retry generation so a retry or delete cannot race publication of imported history. Recheck that boundary after copying and discard or revalidate stale staged work before making it visible. Verify retirement of all remaining MLMD writers and complete a final source reconciliation before removing MLMD, including shared artifacts and historical cache producers. A backfill based only on MLMD IDs cannot account for updates to earlier rows.

Use bounded, restartable writes to the additive storage. Qualify locks on dependencies as well as on the new tables. A bridge version must read the layouts it can encounter during rollback. A restore to 2.18 still uses the documented paired backup and restore procedure. The revised proposal must specify which write generations a rollback preserves and the exact routing and retry protocol before the bridge ships. Defer legacy table cleanup until compatible readers and writers have retired. This outline still requires a proposal change and implementation proof before enabling production Phase 2/3.

**Acceptance.** During the hold, assert that legacy, partially migrated, and transfer-renaming catalogs reach neither migration DDL nor GORM reconciliation through either shipped entry point. Replay the released schema on the supported MySQL versions before lifting the hold. Capture actual startup and migration DDL and verify that the legacy table is not rebuilt. Prove that related reads and writes complete during migration within measured bounds. Verify contention, cancellation, repeated startup, late writes, and rollback. Keep the runtime handoff checks for final reports and readiness. Record large-history duration, peak memory, and temporary disk use. The current lock-timeout test remains useful for recovery coverage.

## 3. Use the released MLMD receive limit in both entry points

**Attempt to disprove.** I checked whether the reader already bounded responses by bytes or the entry points inherited the released limit. The page count is 100 and both dialers use gRPC's 4 MiB default. With 100 artifacts and a 4,505,700-byte response, the repository reader failed at 4 MiB and successfully returned all 100 artifacts at 100 MiB. The released driver used 100 MiB by default and supported a configured override. The reproducer uses an in-process gRPC server. It proves the client-side failure and recovery without making a claim about production memory usage.

**Implementation.** Give the migration package one MLMD client constructor for CLI preflight, CLI copy, and startup. Use the released 100 MiB receive default and honor the released `METADATA_GRPC_MESSAGE_SIZE` override so larger previously supported single records retain a path. Validate the positive byte limit and retain each caller's endpoint, TLS, headers, and context cancellation. For an artifact or execution page refused for message size at that limit, halve the page size, down to one record. Reuse its cursor only if the released MLMD service accepts the size change. If it couples the cursor to page size, restart that list with the smaller fixed size and discard the partial list. Apply the same bounded splitting to multi-execution event requests. Quota and throttling errors follow their own retry policy. Return an actionable error when a single record or an unpageable response exceeds the configured limit. Keep `validate` read-only and describe it as a connectivity, schema, and drain check. Its execution-type probe does not scan history.

**Acceptance.** Exercise both entry points with a page above 4 MiB, an individual record above 4 MiB, a released override, and an aggregate response that requires a smaller batch. Verify that event, context, and type calls use the same limit. Verify no lost or duplicated IDs across page boundaries against the released MLMD service. A configured limit too small for a single record must fail before writes and identify the read and limit.

## 4. Resume interrupted native schema creation safely

**Attempt to disprove.** On MySQL 8.4.10, I applied actual GORM model prefixes to an empty database. The empty catalog passed. The prefix through `run_details` failed the next startup classification because `tasks` was absent. The prefix through `artifacts` failed because `artifact_tasks` was absent. The completed native catalog passed. The old startup path reached GORM reconciliation directly. PostgreSQL uses the same classifier branches, and I did not repeat the partial-catalog test on PostgreSQL.

**Implementation.** Record native bootstrap intent just before the first KFP schema write. Inspect the catalog before acquiring the lock. Use the ordinary classification path for complete unmarked catalogs. For an empty or marked catalog, acquire a lock scoped to the target database and schema on the connection that runs reconciliation. Bound acquisition, recheck the catalog under the lock, and release it on cancellation or failure. Create a dedicated marker only after checking that the KFP catalog is empty across the full owned model inventory. The marker's existence records unfinished native bootstrap. Run the existing GORM reconciliation and check that its required tables, columns, and keys are present before clearing the marker and allowing normal startup. A restarted replica may resume only when the marker exists and the partial catalog is compatible with native initialization. A legacy column, legacy staging table, incompatible object, or MLMD progress marker must prevent this recovery path. Preserve write-free legacy PostgreSQL refusal. Keep an unmarked, incomplete existing schema fail-closed. For an independently confirmed empty interrupted install, document retrying with a new empty database. For a catalog with existing data, direct the operator to recovery from a verified backup.

**Acceptance.** Inject interruption before `tasks` and before `artifact_tasks` through the actual API bootstrap. Restart on MySQL and PostgreSQL, confirm readiness without MLMD, and verify that a second replica joins safely. Exercise an unmarked catalog missing a previously published table, a legacy MySQL catalog, and a legacy PostgreSQL catalog. Verify that the bootstrap path changes none of those catalogs. Fresh and fully native installs must continue to start.

## 5. Resolve retained legacy single-user Workflow ownership from persisted identity

**Attempt to disprove.** The pinned 2.18 release stores the namespace for new runs and repairs old namespace-less runs when it processes a verified Workflow report. That narrows the finding to retained historical rows that have not been reported again. The persistence agent can skip Workflows already marked final. In the restored 2.18 SQL capture, a terminal Workflow with the stored namespace and final label passed. Changing only the run and experiment namespace columns to legacy sentinel values caused `DrainGate.Blockers` to refuse the run while the persisted manifest still contained the execution namespace. This is a historical-row variant of the capture.

**Implementation.** Share namespace resolution between the drain inventory and the migration planner's run-ownership inventory. Keep the existing run and experiment namespace rules. Make the historical fallback available only for an explicitly declared single-user source, through a documented CLI flag and equivalent startup setting. Reject the declaration if the legacy deployment's authoritative configuration shows multi-user mode. Startup also checks that the target is configured for single-user mode. Use strict ownership checks when the source mode is unspecified or multi-user.

When both SQL fields are absent, use the server-persisted Argo runtime object, following the runtime-manifest precedence of Workflow reporting. Verify the saved run ID and name against the SQL record and take the namespace from that saved object. For a live object, require the saved name and namespace and check an available immutable UID. A same-name replacement UID in the claimed namespace blocks migration. A duplicate label in another namespace provides no ownership evidence. Continue checking the live phase and final-report label for an owned object. The saved identity can also establish namespace for a TTL-deleted Workflow when the SQL run has a terminal report. If a transformable source execution claims an unresolved run, report the run ID and refuse before migration writes. Unsupported executions remain skips.

**Acceptance.** Through read-only preflight and the production gate, exercise a historical single-user row with namespace sentinels and a persisted, terminal Workflow in its original namespace. Have the disposable fixture store the UID issued by its own cluster. Recreating an export issues a new UID. Confirm that migration preserves its tasks and artifact links under that namespace. Repeat for a TTL-deleted Workflow with authoritative stored identity, an active Workflow, a Workflow missing its final report, another namespace with the same label, and a same-name replacement UID. Verify that multi-user mode cannot adopt ownership from the single-user fallback.

## 6. Retain eligible child tasks when a parent cannot migrate

**Attempt to disprove.** I checked whether the skip policy or the test contract explicitly requires dropping otherwise valid descendants. The schema permits a NULL parent and the design limits fixup to migrated parents in the same run. The existing regression test expects the drop, and its event lacks a valid named path. I repeated the check with a valid named output event. The supported parent produced two tasks, one artifact, and one link. Changing only the parent's type to an unsupported type produced zero rows in all three tables. The finding holds for eligible child records and their lineage.

**Implementation.** Preserve independently verified tasks from the first pass. In the second pass, resolve a parent only from retained tasks in the same run. Log both IDs when the parent is absent, skipped, or cross-run, and keep the child's parent NULL. Remove cyclic edges from both the Go planner and the fixture generator. Keep each affected task and its artifacts and leave valid descendants linked to their retained immediate parents. Use the resulting verified edges for control-flow refinement and loop iteration provenance. Leave unproven values unspecified or apply the documented generic DAG fallback. Continue constructing artifacts and events from retained tasks. Keep existing validation, UUID derivation, and replay rules. Preserve public task and lineage reads for the detached child. Its original graph position cannot be reconstructed without the parent edge.

**Acceptance.** Replace the test that expects loss with cases for an absent parent, an unsupported parent, and a cross-run parent. Verify the child, its valid named artifact link, and any independently valid descendant survive. Verify a normal same-run parent still links correctly and clean and resumed migrations yield the same graph with the expected NULL parent. Exercise the native task and lineage API reads for the retained child.
