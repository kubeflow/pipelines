## Accessibility qualification

The focused source audit reviewed application navigation, command search, the task inspector, shared dialogs and controls, and creation forms against the current [Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines/blob/main/command.md). This is a scoped engineering audit, not a WCAG conformance assessment.

Confirmed issues and corrections:

- **Inspector resizing:** the existing pointer handle now also exposes a named vertical separator with current, minimum and maximum widths. Left/Right resize by 20 CSS pixels; Home/End choose the bounds. Width survives ordinary rerenders and temporary viewport reduction. When the narrow modal layout removes a focused resize handle, focus moves to the existing Close button. Tests retain Escape dismissal, trigger focus restoration and narrow-screen focus trapping.
- **Dialog descriptions:** simple text dialogs keep their accessible description. Rich dialog content retains its own field, table and list semantics without becoming one flattened description, consistent with the [ARIA dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). Focus trapping and restoration remain covered.
- **Command search:** the existing live status now announces the number of displayed matches when async results arrive. The count describes the bounded visible results, not a global resource total. Existing stale-response and partial-error behavior remains unchanged.
- **Schedule validation:** invalid start/end date-time messages are associated with both corresponding inputs through `aria-describedby` and `aria-invalid`. Correcting the value removes the invalid state and description.
- **JSON parameters:** the Ace input receives the parameter-specific accessible name through supported editor options, with its keyboard accessibility mode enabled. The editor remains lazy loaded and preserves typed parameter callbacks.
- **Forced colors:** switch tracks and thumbs use system colors in forced-colors mode so the state indicator does not disappear. An isolated Chromium probe reproduced the original white thumb on a white track and verified the corrected actual span-based control with emulated forced colors and reduced motion. A durable workflow assertion checks at least 3:1 thumb/track contrast, distinct checked/unchecked positions, and reduced transition duration alongside the existing exactly-once mutation/error-recovery checks.

### Remaining accessibility limits

The unit DOM and automated browsers cannot establish representative screen-reader announcements, actual Windows high-contrast behavior, touch/zoom usability on physical Safari/iOS devices, or every layout at 320 CSS pixels and 400% zoom. The forced-colors probe is browser emulation rather than an operating-system or assistive-technology test. The final production matrix covers pointer/keyboard resizing, focus, dismissal and desktop/narrow viewport transitions. This historical checkpoint originally called for representative assistive-technology and device-user acceptance. The later approved [automated qualification policy](../browser-support.md#automated-qualification) supersedes that manual-testing requirement: untested assistive-technology behavior remains a disclosed limitation and coverage follow-up, with no blanket conformance claim. Supported-browser failures affecting keyboard access or reachable content still block release.

The [maintainer-approved policy](../browser-support.md) supersedes the minimum-version matrix below. Chrome/Edge 111, Firefox 128 and Safari/iOS 16.4 are retired qualification targets. The new stable/enterprise/Safari matrix remains unqualified; no historical result below is relabeled as a run on those channels. The following audit and results describe the earlier checkpoint.

At that checkpoint, the declared minimums were Chrome/Edge 111, Firefox 128, and Safari/iOS 16.4. The explicit Vite targets and Browserslist entries match those minimums. [Tailwind's compatibility guidance](https://tailwindcss.com/docs/compatibility) sets the same Chromium, Firefox and Safari floors. Base UI 1.8's [versioned browser targets](https://github.com/mui/base-ui/blob/v1.8.0/.browserslistrc) include these versions, but the actual Firefox check below demonstrated why a dependency target alone does not establish compatibility. Vite transforms syntax; it [does not automatically polyfill runtime APIs](https://v8.vite.dev/guide/build).

### Firefox 128 activation regression

The real Firefox 128.0 test loaded four native fixture runs, filtered them, and opened and closed an 18-node Run Details graph. It then reproduced an enabled pipeline checkbox failing to select. A separate native-input probe confirmed that a constructed `PointerEvent('click')` delivered the click event without toggling the checkbox or emitting `input`/`change`; both `MouseEvent('click')` and native `input.click()` activated it. Base UI 1.8 uses the constructed pointer event for its hidden checkbox input.

The shared Checkbox/Switch boundary now probes that native behavior once per owner document. On affected engines only, it uses Base UI's documented `inputRef` and `preventBaseUIHandler()` APIs to deliver a modifier-preserving mouse click to the native input. Base UI retains checked state, form values, validation, keyboard behavior and change cancellation. The fallback respects disabled/read-only controls, inherited native-input disabled state and consumer cancellation. It uses no browser-version detection, global event patch or modified dependency files.

Focused tests cover exactly-once pointer and Space changes, the original supported-engine path, controlled and mixed state, modifiers/form values, cancellation, disabled/read-only/group behavior, and forwarded-ref cleanup. React's imperative ref hook synchronizes the external DOM ref; no derived-state effect is introduced. The retained actual Firefox 128.0 smoke passed all seven scenarios on application source `b358c3b4dc6bcf1b47c2ae399b5e85dfc3df0269`, with `index-CMs0YGmE.js` (SHA-256 `d5e8a5dc6a56c0bcaa8bb2c678a9834ed82d209b3b32516e3b0c776c561c29cd`) and `index-BB6Gh9sf.css` (SHA-256 `872fed3daa914cb73dd3272d200481097fabde285213f18666cc43c7ac1c6338`). The [retained result and six screenshot hashes](qualification/browser-floor-firefox128.json) identify this application build. Its native probe still reports pointer-event activation absent and mouse-event activation present, while real pointer and Space interactions successfully toggle both shared primitives. The switch check changes only an unsaved feature draft and verifies stored/runtime flags remain unchanged.

The same session passed Runs filtering, pipeline selection, Run Details graph measurement through inspector open/close, two-run comparison empty states, and a dark dialog at 600 CSS pixels with forward/reverse focus wrapping, Escape dismissal and trigger focus return. Six screenshots were recorded; the cards, inspector, switch and narrow dark dialog were visually inspected. No post-readiness page errors were captured, and session cleanup succeeded. This is scoped minimum-version smoke evidence rather than full minimum-version workflow parity.

The opt-in [WebDriver floor smoke](../../scripts/ui-modernization-browser-floor.mjs) uses a fresh temporary Firefox profile and closes its session in `finally`. It uses the existing native fixture API and production preview without backend mutations. Mozilla's official geckodriver 0.37.1 [supports Firefox 115 ESR and newer](https://firefox-source-docs.mozilla.org/testing/geckodriver/Support.html); its release-asset SHA-256 was verified before use. The smoke records actual capabilities, entry-asset hashes, screenshots, route readiness, required platform features and post-readiness page errors. Its small comparison fixture has two runs but empty parameter and scalar-metric panels, so it does not qualify populated rich comparisons. Its 600 CSS pixel dialog check does not establish 320 pixel/400% zoom or device/assistive-technology acceptance. Errors before initial Runs readiness are not observed, and this is not a complete console or network trace.
