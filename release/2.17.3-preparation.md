# KFP 2.17.3 preparation

This is a maintenance release from `release-2.17`, with backend and SDK security
updates. Python 3.9 support is retained. The fixes PR must merge before the
separate version PR is prepared; no release tag or publication is part of this PR.

## Included changes

- Adapt the Go trust-store fix from [#15025](https://github.com/kubeflow/pipelines/pull/15025),
  source commit `4fe506723b7e5e28b28a17179bb5d8f09a462903`: Go 1.27.3 and its
  digest-pinned builders, including the 2.17 cache-server builder. This addresses
  CVE-2026-111943 in rebuilt Go binaries. The 2.17 branch has no uv pins to update.
- Update certifi to 2026.10.19 in Python runtime and SDK requirements. Unlike
  master, 2.17 did not already include the corresponding Python trust-store fix.
- Update vulnerable Go, Python and frontend dependency versions, with the guarded
  MinIO parser compatibility patch and regression tests from
  [#14865](https://github.com/kubeflow/pipelines/pull/14865).
- Align Argo controller, executor, CLI, manifests and qualification lanes on the
  fixed 4.0.6 patch; retain the existing Argo 3.7 qualification lane.
- Refresh runtime OS packages at image build time, remove unused Cloud CLI from
  visualization, and remove build-only pip/npm from the affected final images.

## Python compatibility and remaining exposure

Python 3.9 remains supported. Security fixes apply wherever compatible with the
selected interpreter. Python 3.9 retains Requests CVE-2026-25645 and urllib3
CVE-2026-44431, CVE-2026-44432, CVE-2026-97687, CVE-2026-97688 and CVE-2026-97689:
the fixed releases require Python 3.10 or newer. Python 3.9.0–3.9.1 additionally
resolve older cryptography releases, retaining CVE-2026-69247, CVE-2026-69248,
CVE-2026-69249 and GHSA-537c-gmf6-5ccf. Python 3.10 or newer is recommended to
receive these dependency fixes; the declared Python minimum remains unchanged.

SDK package metadata reads the interpreter-specific `requirements.in` files.
The committed `requirements.txt` exports continue to target Python 3.11, as on
the maintenance branch before this patch. They are not Python 3.9 lockfiles.

Clean runtime manifest scans do not certify built container images. The
cache-deployer and inverse-proxy require image-level assessment alongside every
other release image, including after the follow-up runtime-image fixes below. Additional
npm advisories for braces and node-forge have no fixed package version in the
reviewed audit. Development/test dependency findings remain separately tracked
in the preparation evidence; this release must not be described as CVE-free.

## Source scan scope

The October 21, 2026 Trivy scan (all severities, development dependencies included,
`--ignore-unfixed`) decreased from 255 to 74 package/advisory occurrences. The
remaining 74 are in the readiness helper (8), frontend integration-test harness

3.11 SDK manifests have zero fixable findings. Python 3.9 environment scans are
separate: 6 findings on 3.9.25 and 10 on 3.9.0, as described above. No suppressions
were added. These counts do not represent unique CVEs or image scan results.

## Release gates and kfpr sequence

1. Review the adapted security fixes and merge the fixes PR into `release-2.17`.
   Recheck #15025 for any changes after the source commit cited above.
2. Use a current `kfpr` installation in a separate Python >=3.11 environment.
   Preserve the real checkpoint separately from any dry-run checkpoint. The
   patch branch is `release-2.17.3`; the backend and SDK versions are both 2.17.3.
3. Run `kfpr run update-version-tags` with explicit `--release-type patch`,
   `--version 2.17.3`, `--previous-release 2.17.2`, `--include-backend`,
   `--include-sdk`, `--patch-prs 15025`, the fork URL and the saved state file.
   This creates `2.17.3-update-version-tags`, builds the legacy Python packages,
   updates metadata and creates a local tag. Include the compatibility caveats
   above in the final changelogs and release descriptions.
4. Verify package contents and supported-Python installation, full frontend
   production build, required CI, cluster smoke/upgrade tests and fresh scans of
   every rebuilt release image. Qualify the actual release artifacts, not scans
   from 2.18 or a source-only scan. Track accepted remaining findings explicitly.
5. Merge the version PR, then publish using the maintenance-branch workflows.
   Review `set_latest` before dispatch: current kfpr image publication sets it to
   true. Complete SDK, documentation and release checkpoints only after their
   respective verification succeeds. Announce only after publication completes.

Do not run the full non-dry-run kfpr flow merely to prepare a draft: it continues
through image/package publication and release creation.

## Follow-up runtime-image fixes after the version PR

Fresh image qualification after #15034 exposed two additional release blockers.
The cache-deployer included an unused Cloud SDK with vulnerable bundled tools.
The inverse-proxy inherited an obsolete Debian runtime and Go binary; its package
installation failed with HTTP 404 responses before an image could be produced.

The cache-deployer now installs only Bash, CA certificates, curl, jq, kubectl and
OpenSSL on a pinned Alpine base. The inverse-proxy rebuilds the pinned agent
source using Go 1.27.3 and patched dependencies, uses a supported Python runtime,
and retains Cloud SDK authentication commands needed by its registration script.
Both images rebuild the same pinned kubectl source with the patched Go toolchain. The proxy preserves its agent
configuration defaults and existing registration command.

Run the built-image regression tests with `KFP_CACHE_DEPLOYER_IMAGE` and
`KFP_INVERSE_PROXY_IMAGE` set to the corresponding local image tags. These tests
check runtime tools and scripts without requiring cluster credentials. They do
not replace cluster smoke tests or fresh vulnerability scans of the complete
release image matrix. Requalify the exact merged follow-up commit before tagging;
the earlier version-PR merge and local tag do not contain these fixes.

Use Trivy comprehensive detection for image scans so embedded Go modules in
OS-packaged binaries are included. The cache deployment script's existing
server-version-dependent kubectl download remains outside built-image scan
coverage; do not describe these scans as qualification of that downloaded binary.

Local follow-up validation: cache-deployer AMD64 and ARM64 each passed two
runtime/security regression tests and comprehensive scans with zero findings,
including explicit kubectl Go-module coverage. Proxy AMD64 passed its runtime
regression and four existing Python tests; comprehensive scanning found zero
fixable findings and retained 293 unfixed occurrences. These results qualify the
changed images at this point in time, not the complete release image matrix.
